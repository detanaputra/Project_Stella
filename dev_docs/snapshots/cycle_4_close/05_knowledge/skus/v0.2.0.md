## 2026-08-27 — Cycle 2 (v0.2.0)

### SKU-02-01 — v0.2.0 planning: Metrics tab, Gensim over OCTIS, metrics on TopicResult
- **Evidence:** commit `ada3a03`
- **Context:** Cycle 2 (v0.2.0) planning. The roadmap required topic quality metrics (NPMI, C_V, UMass coherence, Topic Diversity). The initial requirement named OCTIS as the metric library. Design questions arose: where to display the metrics, which library to use, where to store the computed values, and how to handle the single-event observer mechanism as the app grows.
- **Design Decision:** Metrics go in a new "Metrics" tab (added to the main Notebook after Analysis once a result exists), not the summary tab — 4 gauge/donut charts, one per metric, each showing the model's single averaged value. Use Gensim's `CoherenceModel` for the three coherence measures and implement Topic Diversity in-app; OCTIS was rejected after a footprint check (the `octis` package is 0.13 MB but pulls torch ~106 MB wheel / ~500 MB+ installed, spacy, sentence-transformers — 1–2 GB installed and 1 GB+ on a PyInstaller bundle — and pins `scikit-learn==1.1.0`, wheels only for Python 3.8–3.10, incompatible with the app's Python 3.11+ and `scikit-learn==1.7.1`). Store metrics on a new `TopicResult.quality_metrics` field (not a parallel `AppState` field) so each model's metrics travel with its result — preparing for multi-model. Keep the single `STATE_CHANGED` observer mechanism with a cheap-subscriber discipline (expensive work in controllers' background threads; subscribers guard on the field they care about).
- **Observation:** v0.2.0 scope was decided and recorded (ROADMAP, decisions D-020/021/022); the `TopicResult` contract gained `quality_metrics` in `api.md` and the dataclass.
- **Insight:** A footprint check before adopting a research library can save gigabytes of bundle size and dependency conflicts; storing evaluation output on the result object (rather than app state) is the multi-model-ready shape; the single-event observer stays cheap when subscribers guard instead of recalculating.

### SKU-02-02 — MouseWheel scrolling in the parameter panels
- **Evidence:** commits `ed32375`, `0035cba`, `3d6bc3d`
- **Context:** The algorithm settings panel and the wizard's hyperparameter panel are scrollable via a Canvas + Scrollbar, but users had to grab the scrollbar to scroll the parameter list.
- **Design Decision:** Bind the mouse wheel to the scrollable canvas and recursively to the dynamically-created parameter widgets. Cross-platform: `<MouseWheel>` for Windows/macOS (delta normalization — ±120 per notch vs small macOS values) and `<Button-4>`/`<Button-5>` for Linux. Re-bind after each form rebuild (the settings panel rebuilds its sections on structural change).
- **Observation:** Both parameter panels scroll with the wheel; verified with a headless Tk smoke test.
- **Insight:** Tkinter canvases do not scroll on the wheel by default — you must bind it, and the binding must reach the dynamically-created child widgets, not just the canvas; delta values differ per platform, so normalization is required.

### SKU-02-03 — Topic quality backend: Gensim coherence + hand-rolled Topic Diversity
- **Evidence:** commit `e7d5996`
- **Context:** v0.2.0 needs NPMI, C_V, UMass coherence and Topic Diversity computed after training, in the background.
- **Design Decision:** New `topic_quality` service. Coherence via Gensim's `CoherenceModel` (`u_mass`, `c_v`, `c_npmi`) with `processes=1`; Topic Diversity hand-rolled (Gensim does not provide it). The pipeline computes metrics after training and sets `result.quality_metrics`; a metric failure does not fail the analysis.
- **Observation:** All four metrics compute reliably and fast on a small corpus. The `processes=1` fix was necessary: Gensim's default multiprocessing for `c_v`/`c_npmi` raises "bootstrapping phase" errors from a GUI background thread on macOS spawn.
- **Insight:** Gensim's sliding-window coherence measures use multiprocessing by default — force `processes=1` in a GUI app to avoid spawn issues (and it is fast for research corpora); coherence is per-topic, so average to one value per metric.

### SKU-02-04 — Metrics tab UI: MetricPanel gauges
- **Evidence:** commit `a1fe3d4`
- **Context:** Display the four topic quality metrics to the user after training.
- **Design Decision:** New `MetricPanel` (ttk.Frame) rendering four matplotlib gauge/donut charts from `result.quality_metrics` (one per metric, per-metric scales). `MainWindow` subscribes to state and adds the "Metrics" tab after Analysis once a result exists, removing it when `current_result` is cleared. The panel uses a sentinel guard (distinct from `None`) so it re-renders only when the result object changes.
- **Observation:** The Metrics tab appears after training, shows four gauges, and disappears when the result is cleared; verified with a headless Tk smoke test. The initial guard keyed on `None` skipped the first render — the sentinel fixed it.
- **Insight:** A render guard keyed on `None` collides with the legitimate "no result yet" state (D-014) — use a distinct sentinel; a dynamically-added tab tied to state gives a clean lifecycle without a permanent placeholder.
