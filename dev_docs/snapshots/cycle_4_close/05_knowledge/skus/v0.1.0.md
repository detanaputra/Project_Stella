## 2026-08-08 — Scaffold, architecture, and initial build

### SKU-01-01 — MVC architecture foundation (was SKU-001/002/003)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** Need a starting point for the ttkbootstrap desktop application; the flat scaffold would not scale as the app grew; the accepted build plan had to become a working application.
- **Design Decision:** Scaffolded a minimal single-file MVC (`requirements.txt`, `model.py`, `view.py`, `controller.py`, `main.py`), moved it into `app/models`, `app/views`, `app/controllers` packages, then built the full MVC application: `AppState` (observer state), `TopicResult`, `BaseAlgorithm` + `BERTopicAlgorithm`, `DataLoader`, `ProjectService`, controllers, and the first UI panels.
- **Observation:** The minimal scaffold became a complete MVC application with BERTopic support.
- **Insight:** A single-file MVC skeleton anchors the data flow early; a package-per-layer layout keeps each layer independently importable and testable; a centralized state plus an algorithm abstraction lets the UI stay algorithm-agnostic — the foundation for later LDA/NMF. *(D-001)*

### SKU-01-02 — 3-column layout (was SKU-004)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** The main window needed a 3-column layout.
- **Design Decision:** Rewrote the layout with `ttk.PanedWindow` (outer: toolbox left, Notebook right) and an inner PanedWindow (summary frame left, parameters right).
- **Observation:** The main window now matches the 3-column paned layout.
- **Insight:** Nested PanedWindows give each content region a resizable, user-adjustable partition.

## 2026-08-10 — Panel extraction and the wizard

### SKU-01-03 — 4-step wizard (was SKU-005, + SKU-013)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** Non-technical users need guided model setup.
- **Design Decision:** Created `app/views/wizard/` with `panel_algorithm.py`, `panel_preview.py`, `panel_hyperparams.py`, `panel_summary.py`, `wizard_main.py`; linked it from the File menu.
- **Observation:** A 4-step Topic Model Wizard guides setup: algorithm/file → hyperparameters → preview → summary. A later "loading indefinitely" report was a conceptual mismatch — Next only navigates; only Train begins processing.
- **Insight:** Breaking setup into sequential steps lowers cognitive load compared to one dense form; the wizard's Next button navigates, not trains — the LoadingPanel only appears on Train. *(D-002)*

## 2026-08-11 — Loading panel

### SKU-01-04 — Loading panel owned by MainWindow (was SKU-006/007)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** Training runs with no visible progress feedback; the loading panel was owned by the wizard, so it was destroyed when the wizard closed.
- **Design Decision:** Created `app/views/panels/loading_panel.py` with an indeterminate progress bar; wired the wizard's Train action to it; then moved `show_loading_panel()` to `MainWindow`; the panel subscribes to `AppState` and closes itself when `analysis_in_progress` turns false.
- **Observation:** Users get visible progress feedback; the panel persists past wizard closure and auto-closes on completion.
- **Insight:** Even indeterminate feedback signals the app is working during long operations; a widget's lifetime follows its parent — owning the panel at the app level and tying it to state (not a view) makes it survive the wizard. *(D-003)*

## 2026-08-12 — Observer cleanup and summary tables

### SKU-01-05 — Parameter plumbing is the risk surface (was SKU-008)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** BERTopic throws `'bool' object is not iterable` during training.
- **Design Decision:** Investigated the parameter plumbing between UI, state, and `BERTopicAlgorithm.train()`; compared with `notebooks/test_sample.ipynb`.
- **Observation:** Identified how a boolean/mismatched parameter reaches BERTopic's expected sequence.
- **Insight:** Parameters cross many layers (UI → state → algorithm); their types must be validated at the algorithm boundary.

### SKU-01-06 — Weak-ref observers + destroyed-widget guard (was SKU-009/015)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** Destroyed observer subscribers were not being garbage collected; later, `invalid command name` errors showed callbacks still touching destroyed widgets.
- **Design Decision:** Reworked `app/models/app_state.py` — observers stored via `weakref.WeakMethod`; `notify()`/`process_events()` drop dead references; guarded `LoadingPanel` state updates against destroyed widgets.
- **Observation:** Subscribed widgets no longer leak memory after destruction; callbacks no longer touch destroyed widgets during the poll loop.
- **Insight:** Strong observer references keep destroyed widgets alive; weak references break that retention cycle — but Tk callbacks can still fire after destruction, so guard where stale widgets are touched. *(D-004)*

### SKU-01-07 — Summary tables (was SKU-010)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** Results displayed as plain labels rather than structured data.
- **Design Decision:** `summary_panel.py` renders Treeview tables for topics and per-document assignments, shown only when a result exists.
- **Observation:** Results display as structured tables instead of plain labels.
- **Insight:** Gated tables (render only when a result exists) keep the panel honest between runs.

## 2026-08-16 — Visualizations, retrain, and bug fixes

### SKU-01-11 — Browser visualizations via pywebview in a separate process (was SKU-017/018/020)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** Interactive BERTopic visualizations are needed; `WebViewException('pywebview must be run on a main thread.')`; four visualization buttons were needed.
- **Design Decision:** Created `app/views/panels/visualizations/bertopic_viz_panel.py`; added `pywebview`; wired into `toolbox_panel.py`; `main.py` calls `multiprocessing.freeze_support()` and the visualization launches in a separate process; generalized the viz panel with an `_on_request_visualization(method_name, title)` launcher and four buttons.
- **Observation:** Interactive BERTopic plots render in a webview window off the main thread; all four visualizations are available from the toolbox.
- **Insight:** Rendering BERTopic's native Plotly plots in a lightweight webview avoids bundling a browser engine; Tk's main loop is occupied by the UI — offloading the webview to a separate process satisfies pywebview's main-thread requirement; a single launcher keyed by method name removes per-button duplication. *(D-009)*

### SKU-01-12 — Attribute shadowing is silent breakage (was SKU-019)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** `self.state` shadowed the Tk widget's own `state` property.
- **Design Decision:** Renamed `self.state` → `self.appState: AppState` across all panels and controllers.
- **Observation:** No more accidental overriding of the Tk widget `state` property.
- **Insight:** An attribute that collides with a Tk widget property silently changes widget behavior — naming must avoid the shadow.

### SKU-01-13 — Retrain bound to shown parameters via traces (was SKU-021)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** Retrain reverted parameters to defaults and trained with defaults.
- **Design Decision:** Traced the UI↔state disconnect; bound each section's widgets to `algorithm_params` via traces.
- **Observation:** Parameter changes now flow to state; Retrain uses the shown values.
- **Insight:** The form and the state are separate stores — they must be kept in sync (here, by traces) or retrains silently use stale values. *(D-010)*

### SKU-01-14 — Instrument the pipeline with debug logging (was SKU-022/023)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** After training, the summary panel didn't display the result; it printed `current_result = False`.
- **Design Decision:** Verified the subscription; added debug logging to `_on_state_changed` and to `AnalysisController` (load count, process return, exceptions).
- **Observation:** The subscriber is correct — the problem was in the pipeline, not the notification; isolated the failure to the training path.
- **Insight:** Logging the suspected layer disambiguates "not notified" from "notified but empty"; instrumenting each stage of a pipeline turns a vague symptom into a specific failing stage.

### SKU-01-15 — Normalize BERTopic output before mapping documents (was SKU-024/025)
- **Evidence:** commits `7b88c71`, `f0573ff` (v0.1.0 build — single initial commit)
- **Context:** `TypeError: 'numpy.float64' object is not iterable` in `bertopic.py`; the doc-topic table assigned almost every document to Topic 0 despite 8 topics.
- **Design Decision:** Fixed the 1-D `probs` case (single topic) by reshaping before mapping; fixed the internal-cluster-id → final-topic-id mapping in the `probs` extraction.
- **Observation:** Single-topic runs no longer crash the doc-probability mapping; documents now map to the correct topics.
- **Insight:** BERTopic's probability shape differs between single-topic and multi-topic runs — normalize the shape before iterating; BERTopic's internal cluster ids differ from the final topic ids — a missing translation silently collapses everything to one topic. *(D-019)*

## 2026-08-17 — Codebase audit and high-severity fixes

### SKU-01-16 — Read-only audit before fixing (was SKU-026)
- **Evidence:** `dev_docs/snapshots/cycle_1_close/audit.md` (archived)
- **Context:** The codebase needed a bug audit, and the user explicitly required it be read-only.
- **Design Decision:** Read all 45 Python source files plus the docs and the training notebook; verified suspected bugs with targeted checks; wrote `audit.md` with findings H1–H6 (high), M1–M8 (medium), L1–L8 (low). Made no code changes.
- **Observation:** A read-only audit was delivered; the BERTopic parameter plumbing was flagged as the core risk.
- **Insight:** A read-only audit (no edits) preserves a clean baseline while delivering prioritized, verifiable findings before any change is made. *(D-011)*

### SKU-01-17 — `.gitignore`: root cause + committed ignore file (was SKU-027/029)
- **Evidence:** commit `baa3443`
- **Context:** The `.claude` folder appeared tracked, and the user asked to exclude it; the repo had no tracked `.gitignore`.
- **Design Decision:** Investigated why `.claude` was tracked and identified the root cause — the repo had no committed `.gitignore`; created the project `.gitignore` with a `.claude/` exclusion and restored compiled artifacts from tracking.
- **Observation:** The `.claude` folder was only "tracked" because the project's `.gitignore` was never committed; Claude Code worktree/plan files and compiled artifacts stay out of git.
- **Insight:** "Tracked" folders are often just un-ignored files — find the root cause (no committed ignore file) before writing an ignore rule; a committed `.gitignore` is only half the fix — already-tracked artifacts must be untracked explicitly, or they remain in the index. *(D-015)*

### SKU-01-18 — Distinguish structural from value changes (was SKU-028)
- **Evidence:** commit `10b822e`
- **Context:** H1 audit finding: the parameter form rebuilt itself on every keystroke, destroying the edit mid-typing.
- **Design Decision:** `AlgorithmSettingsPanel._render()` now rebuilds the parameter form only on structural changes instead of on every keystroke.
- **Observation:** H1 (form destroying itself mid-edit) is fixed.
- **Insight:** Distinguishing structural changes from value changes prevents a rebuild loop where the form under the cursor is recreated by the keystroke it receives. *(D-012)*

### SKU-01-19 — Safe force-push with `--force-with-lease` (was SKU-030)
- **Evidence:** merge commit `020e47c` (audit branch reconciled and merged to `main`)
- **Context:** The user reported having no changed files in their working copy — the branch claim was stale.
- **Design Decision:** Verified `main` had moved on; rebased `worktree-code-audit` onto current `main`, dropping the redundant `.gitignore` commit, and force-pushed with `--force-with-lease`.
- **Observation:** The branch history was reconciled with `main`; the stale claim was corrected against the live repo state.
- **Insight:** Rebasing drops a redundant commit instead of duplicating it, and `--force-with-lease` makes a force-push safe by failing if the remote moved unexpectedly. *(D-016)*

### SKU-01-20 — High-severity audit fixes as one batch (was SKU-031)
- **Evidence:** commit `a02d9f5`
- **Context:** The user verified the H1 fix worked and asked to fix the rest of the top-5 findings.
- **Design Decision:** Implemented H2–H6 — wizard default-parameter sync, wiring the five documented BERTopic hyperparameters into `train()`, showing the parameter UI before the first run, exception-safe event polling, and default parameter initialization.
- **Observation:** All six high-severity findings are fixed.
- **Insight:** Delivering the whole high-severity class in one commit keeps the branch's fix history readable and gives one testable unit.

## 2026-08-18 — Medium/low-severity fixes, v0.1.0 release, v0.2.0 setup

### SKU-01-21 — Thread-safe UI dispatch is the linchpin (was SKU-032)
- **Evidence:** commit `fdd421b` (verified with headless tests)
- **Context:** The medium-severity findings remained to be implemented.
- **Design Decision:** Implemented M1–M8 — thread-safe UI dispatch (`AppState.call_on_main`), training re-entrancy guard, matplotlib figure cleanup, summary-panel rebuild guard + row cap, real export panel and offline Plotly visualizer, DataLoader CSV/encoding edge cases, debug-print removal, HDBSCAN `min_cluster_size`.
- **Observation:** All eight medium-severity fixes were implemented, verified with headless tests.
- **Insight:** Thread-safe UI dispatch is the linchpin M-fix — several others only become safe once state changes reach the UI on the main thread. *(D-013)*

### SKU-01-22 — Sentinel guard distinct from `None` (was SKU-033)
- **Evidence:** commit `0383ce1` (verified with a live-Tk test)
- **Context:** `AttributeError: 'SummaryPanel' object has no attribute '_last_result'` at line 39 despite initialization at line 20.
- **Design Decision:** Fixed the initialization order (the attribute must be set before `_build_ui()` runs `_render()`) and used a sentinel distinct from `None` so the placeholder still renders on a fresh start.
- **Observation:** The M3 render guard no longer crashes at startup.
- **Insight:** A guard keyed on `None` collides with the legitimate "no result yet" state — a distinct sentinel, plus initializing before the build that reads it, resolves both. *(D-014)*

### SKU-01-23 — Low-severity fixes + `audit.md` as source of truth (was SKU-034)
- **Evidence:** commit `86f8dd5`
- **Context:** The low-severity findings were pending; the user noted L2 was fixed but `audit.md` had not been updated.
- **Design Decision:** Implemented L1–L8 — deleted dead views/stub menus (real Edit menu, theme switcher on App Settings), parameter validation (UMAP/ngram clamps), LoadingPanel stacking guard, stop-words path handling, notebook bugs, project-load validation, milestone-based progress; updated `audit.md` including the L2 status.
- **Observation:** All low-severity findings fixed; every fix status is now recorded in `audit.md`.
- **Insight:** Keeping `audit.md` in sync with each fix makes it the single source of truth for what is done versus outstanding.

### SKU-01-24 — Release workflow: merge → verify → delete → fresh branch (was SKU-035)
- **Evidence:** merge commit `020e47c` (PR #1 — v0.1.0 released to `main`; `v0.2.0` branch created from `main`)
- **Context:** The user merged the audit branch into `main`, deleted it on GitHub, called the release v0.1.0, and asked for cleanup plus a new branch.
- **Design Decision:** Verified every branch commit was already on `main`; removed the `code-audit` worktree and branch; pruned the stale remote ref; created and checked out `v0.2.0` from `main`.
- **Observation:** v0.1.0 is released; the `v0.2.0` branch is ready for the next feature list.
- **Insight:** Verifying all commits reached `main` before deleting the branch prevents silent work loss, and branching from current `main` gives a clean baseline for the next release. *(D-017)*

- **Evidence:** commit `50ec71c`
- **Context:** The released v0.1.0 feature set needed to be documented; v0.2.0 features would come later.
