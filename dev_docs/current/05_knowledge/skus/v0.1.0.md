# Structured Knowledge Units — v0.1.0

Structured Knowledge Units (SKUs) for the v0.1.0 build cycle (2026-08-08 → 2026-08-17), reconstructed from `logs.md`.

- **SKU IDs are global** across the project (`SKU-001` … `SKU-036`; v0.1.1 continues from `SKU-026`).
- **Triaged:** 25 SKUs retained (transferable decisions/learnings). 19 trivial interactions demoted to the appendix — not SKUs.
- Structure per `dev_docs/llm_guidance/sku_instruction.md`: Context / Design Decision / Observation / Insight. An optional **Evidence:** field links a commit or artefact.

## 2026-08-08 — Scaffold, architecture, and initial build

### SKU-001 — 2026-08-08 07:14 UTC
- **Context:** Need a starting point for the ttkbootstrap desktop application.
- **Design Decision:** Scaffolded a minimal single-file MVC: `requirements.txt`, `model.py`, `view.py`, `controller.py`, `main.py`.
- **Observation:** A minimal runnable MVC scaffold was in place.
- **Insight:** A single-file MVC skeleton anchors the data flow early, making later structure decisions mechanical.

### SKU-002 — 2026-08-08 07:59 UTC
- **Context:** The flat scaffold files would not scale as the app grew.
- **Design Decision:** Created `app/models`, `app/views`, `app/controllers` packages (each with `__init__.py`) and moved the scaffold files into them.
- **Observation:** The project now follows a conventional MVC package layout.
- **Insight:** A package-per-layer layout keeps each layer independently importable and testable as features expand.

### SKU-003 — 2026-08-08 08:44 UTC
- **Context:** The accepted build plan had to become a working application.
- **Design Decision:** Built the full MVC application: `AppState` (observer state), `TopicResult`, `BaseAlgorithm` + `BERTopicAlgorithm`, `DataLoader`, `ProjectService`, controllers, and the first UI panels.
- **Observation:** The minimal scaffold became a complete MVC application with BERTopic support.
- **Insight:** A centralized state plus an algorithm abstraction lets the UI stay algorithm-agnostic — the foundation for later LDA/NMF. *(recorded as D-001 in `03_control/decisions.md`)*

### SKU-004 — 2026-08-08 18:24 UTC
- **Context:** The main window needed a 3-column layout.
- **Design Decision:** Rewrote the layout with `ttk.PanedWindow` (outer: toolbox left, Notebook right) and an inner PanedWindow (summary frame left, parameters right).
- **Observation:** The main window now matches the 3-column paned layout.
- **Insight:** Nested PanedWindows give each content region a resizable, user-adjustable partition.

## 2026-08-10 — Panel extraction and the wizard

### SKU-005 — 2026-08-10 09:03 UTC
- **Context:** Non-technical users need guided model setup.
- **Design Decision:** Created `app/views/wizard/` with `panel_algorithm.py`, `panel_preview.py`, `panel_hyperparams.py`, `panel_summary.py`, `wizard_main.py`; linked it from the File menu.
- **Observation:** A 4-step Topic Model Wizard guides setup: algorithm/file → preview → hyperparameters → summary.
- **Insight:** Breaking setup into sequential steps lowers cognitive load compared to one dense form.

## 2026-08-11 — Loading panel

### SKU-006 — 2026-08-11 20:03 UTC
- **Context:** Training runs with no visible progress feedback.
- **Design Decision:** Created `app/views/panels/loading_panel.py` with an indeterminate progress bar; wired the wizard's Train action to it.
- **Observation:** Users now get visible progress feedback while training runs.
- **Insight:** Even indeterminate feedback signals the app is working during long operations.

### SKU-007 — 2026-08-11 20:37 UTC
- **Context:** The loading panel was owned by the wizard, so it was destroyed when the wizard closed.
- **Design Decision:** Moved `show_loading_panel()` to `MainWindow`; the panel subscribes to `AppState` and closes itself when `analysis_in_progress` turns false.
- **Observation:** The panel now persists past wizard closure and auto-closes on completion.
- **Insight:** A widget's lifetime follows its parent — owning the panel at the app level and tying it to state (not a view) makes it survive the wizard. (`D-003`)

## 2026-08-12 — Observer cleanup and summary tables

### SKU-008 — 2026-08-12 12:32 UTC
- **Context:** BERTopic throws `'bool' object is not iterable` during training.
- **Design Decision:** Investigated the parameter plumbing between UI, state, and `BERTopicAlgorithm.train()`; compared with `notebooks/test_sample.ipynb`.
- **Observation:** Identified how a boolean/mismatched parameter reaches BERTopic's expected sequence.
- **Insight:** Parameters cross many layers (UI → state → algorithm); their types must be validated at the algorithm boundary.

### SKU-009 — 2026-08-12 19:30 UTC
- **Context:** Destroyed observer subscribers were not being garbage collected.
- **Design Decision:** Reworked `app/models/app_state.py` — observers stored via `weakref.WeakMethod`; `notify()`/`process_events()` drop dead references.
- **Observation:** Subscribed widgets no longer leak memory after destruction.
- **Insight:** Strong observer references keep destroyed widgets alive; weak references break that retention cycle. (`D-004`)

### SKU-010 — 2026-08-12 20:36 UTC
- **Context:** Results displayed as plain labels rather than structured data.
- **Design Decision:** `summary_panel.py` renders Treeview tables for topics and per-document assignments, shown only when a result exists.
- **Observation:** Results display as structured tables instead of plain labels.
- **Insight:** Gated tables (render only when a result exists) keep the panel honest between runs.

## 2026-08-13 — Modular hyperparameters

### SKU-011 — 2026-08-13 21:02 UTC
- **Context:** Implement the hyperparameter reference from `BERTopicHyperparams.md`.
- **Design Decision:** Created `app/views/panels/hyperparams/` with `base_section.py`, `bertopic_section.py`, `umap_section.py`, `hdbscan_section.py`; refactored the wizard's hyperparameter panel to use them; added prefixed keys (`umap_*`, `hdbscan_*`).
- **Observation:** BERTopic/UMAP/HDBSCAN settings are modular, reusable sections with collision-free state keys.
- **Insight:** Reusable sections plus key prefixes keep each algorithm's parameters isolated and prevent state collisions. (`D-005`)

## 2026-08-14 — Wizard fixes, save/load

### SKU-012 — 2026-08-14 05:45 UTC
- **Context:** The wizard's Next/Previous buttons disappeared.
- **Design Decision:** Fixed pack order in `wizard_main.py` — the notebook was consuming all vertical space.
- **Observation:** Navigation buttons are visible again.
- **Insight:** In Tkinter, pack order determines geometry — widgets packed after a greedily-expanding child receive no space.

### SKU-013 — 2026-08-14 06:13 / 06:18 UTC
- **Context:** "It is loading indefinitely" when clicking Next from the algorithm to the hyperparameter panel.
- **Design Decision:** Investigated the analysis pipeline and LoadingPanel close conditions.
- **Observation:** The LoadingPanel only appears on Train; the wizard's Next button does not start training.
- **Insight:** The symptom came from a conceptual mismatch — Next only navigates; only Train begins processing.

### SKU-014 — 2026-08-14 07:51 UTC
- **Context:** After an edit the whole hyperparameter section disappeared, including BERTopic.
- **Design Decision:** Restored the section-instantiation block that was accidentally removed in the prior edit.
- **Observation:** All three sections render again in the wizard.
- **Insight:** The section-instantiation block is the wiring that makes modular sections visible — removing it silently deletes the UI.

### SKU-015 — 2026-08-14 07:55 UTC
- **Context:** `invalid command name ".!loadingpanel.!frame.!label"` — investigate the weak-ref cleanup mechanism.
- **Design Decision:** Guarded `LoadingPanel` state updates against destroyed widgets; tightened `AppState` observer cleanup.
- **Observation:** Callbacks no longer touch destroyed widgets during the poll loop.
- **Insight:** Weak references reduce leaks but Tk callbacks can still fire after destruction — guard where stale widgets are touched.

### SKU-016 — 2026-08-14 10:29 UTC
- **Context:** Projects need persistence.
- **Design Decision:** Implemented `_on_save()` / `_on_load()` in `file_menu.py`; the save extension is `.stella`; wired to `ProjectService`.
- **Observation:** Projects can be saved to and loaded from `.stella` files.
- **Insight:** A project-file format (rather than raw exports) gives users session continuity. (`D-007`)

## 2026-08-16 — Visualizations, retrain, and bug fixes

### SKU-017 — 2026-08-16 10:37 UTC
- **Context:** Interactive BERTopic visualizations are needed.
- **Design Decision:** Created `app/views/panels/visualizations/bertopic_viz_panel.py`; added `pywebview==5.2.1`; wired into `toolbox_panel.py`; renders `current_result.visualize_topics()` via pywebview.
- **Observation:** Interactive BERTopic plots render in a webview window.
- **Insight:** Rendering BERTopic's native Plotly plots in a lightweight webview avoids bundling a browser engine. (`D-009`)

### SKU-018 — 2026-08-16 10:46 UTC
- **Context:** `WebViewException('pywebview must be run on a main thread.')`.
- **Design Decision:** `main.py` calls `multiprocessing.freeze_support()`; the visualization launches in a separate process.
- **Observation:** The webview now runs off the main thread correctly.
- **Insight:** Tk's main loop is occupied by the UI — offloading the webview to a separate process satisfies pywebview's main-thread requirement.

### SKU-019 — 2026-08-16 11:59 UTC
- **Context:** `self.state` shadowed the Tk widget's own `state` property.
- **Design Decision:** Renamed `self.state` → `self.appState: AppState` across all panels and controllers.
- **Observation:** No more accidental overriding of the Tk widget `state` property.
- **Insight:** An attribute that collides with a Tk widget property silently changes widget behavior — naming must avoid the shadow.

### SKU-020 — 2026-08-16 12:07 UTC
- **Context:** Four visualization buttons were needed: heatmap, bar chart, term rank, hierarchy.
- **Design Decision:** Generalized the viz panel with an `_on_request_visualization(method_name, title)` launcher and four buttons.
- **Observation:** All four BERTopic visualizations are available from the toolbox.
- **Insight:** A single launcher keyed by method name removes per-button duplication.

### SKU-021 — 2026-08-16 12:29 UTC
- **Context:** Retrain reverted parameters to defaults and trained with defaults.
- **Design Decision:** Traced the UI↔state disconnect; bound each section's widgets to `algorithm_params` via traces.
- **Observation:** Parameter changes now flow to state; Retrain uses the shown values.
- **Insight:** The form and the state are separate stores — they must be kept in sync (here, by traces) or retrains silently use stale values. (`D-010`)

### SKU-022 — 2026-08-16 12:40 UTC
- **Context:** After training, the summary panel didn't display the result.
- **Design Decision:** Verified the subscription; added debug logging to `_on_state_changed`.
- **Observation:** The subscriber is correct — the problem was in the pipeline, not the notification.
- **Insight:** Logging the suspected layer disambiguates "not notified" from "notified but empty."

### SKU-023 — 2026-08-16 12:48 UTC
- **Context:** It prints `current_result = False` — the issue is in the training pipeline.
- **Design Decision:** Added pipeline debug logging to `AnalysisController` (load count, process return, exceptions).
- **Observation:** Isolated the failure to the training path.
- **Insight:** Instrumenting each stage of a pipeline turns a vague symptom into a specific failing stage.

### SKU-024 — 2026-08-16 20:39 UTC
- **Context:** `TypeError: 'numpy.float64' object is not iterable` in `app/models/algorithms/bertopic.py`.
- **Design Decision:** Fixed the 1-D `probs` case (single topic) by reshaping before mapping.
- **Observation:** Single-topic runs no longer crash the doc-probability mapping.
- **Insight:** BERTopic's probability shape differs between single-topic and multi-topic runs — normalize the shape before iterating. (`D-019`)

### SKU-025 — 2026-08-16 21:12 UTC
- **Context:** The doc-topic table assigned almost every document to Topic 0 despite 8 topics.
- **Design Decision:** Fixed the internal-cluster-id → final-topic-id mapping in the `probs` extraction.
- **Observation:** Documents now map to the correct topics.
- **Insight:** BERTopic's internal cluster ids differ from the final topic ids — a missing translation silently collapses everything to one topic. (`D-019`)
