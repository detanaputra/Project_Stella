# Structured Knowledge Units — v0.4.0

#decision #design #learn

Structured Knowledge Units (SKUs) for the v0.4.0 build cycle (WP1 — topic refinement; WP4 — document exploration, 2026-09-06), created from the design-changing work of Cycle 4. WP2 (retire pywebview — dead-code removal) and WP3 (UI polish — metrics explanations, dialog centring, MVP option limiting) are treated as trivial and produce no SKUs.

- **SKU IDs are cycle-coded:** `SKU-04-NN` (cycle 4, sequential number).
- **Triaged:** only the user-visible design decisions and learnings produce SKUs; implementation trivia is folded into the related SKU or omitted.
- Structure per `dev_docs/llm_guidance/sku_instruction.md`: Context / Design Decision / Observation / Insight, plus an **Evidence:** field with the commit ref(s).

## 2026-09-06 — Cycle 4 (v0.4.0), WP1: topic refinement

### SKU-04-01 — Shared result-builder for training and refinement
- **Evidence:** commit `41a36a7` (`app/models/algorithms/bertopic.py` — `_build_result`)
- **Context:** Topic refinement (merge/delete) mutates the BERTopic model via BERTopic's native `delete_topics`/`merge_topics`. After a mutation the result (topics, doc-topics, `model_info`) must be rebuilt — but the "extract topics + doc-topics from a fitted model" logic lived inside `BERTopicAlgorithm.train`, so refinement would have had to duplicate it.
- **Design Decision:** Extracted that logic into a module-level `_build_result(model, texts, params)` helper, used by both `train()` and the new `merge_topics`/`delete_topics` methods.
- **Observation:** Training and refinement now produce identical result shapes; the doc-topic mapping (prob-column → topic id) stays correct after BERTopic's `topic_mapper_` remaps topic ids on merge/delete.
- **Insight:** BERTopic's output shape and internal topic-id space vary (single-topic probs are 1-D; merge/delete remap ids through `topic_mapper_`), so one result-builder is the correctness cliff — a shared builder means the same normalisation serves both the train path and the refinement path, and a divergence between them would silently mislabel documents.

### SKU-04-02 — Checkbox-column selection without native checkboxes
- **Evidence:** commit `41a36a7` (`app/views/panels/summary_panel.py` — `_create_topics_table`, `_on_topic_click`)
- **Context:** Topic refinement needs multi-select (check 2+ topics to merge, 1+ to delete/label). Neither `ttk.Treeview` nor ttkbootstrap's `Tableview` has a native checkbox column (the ttkbootstrap maintainer confirmed this).
- **Design Decision:** Added a leading ☐/☑ glyph column; clicking **anywhere on a row** toggles the glyph and mirrors the state into the Treeview's native selection (`selectmode="none"`, `selection_add`/`selection_remove`) so the row also highlights with the theme's selection colour.
- **Observation:** Users toggle topics by clicking any part of a row; the glyph and the row highlight stay in sync; the refinement toolbar enablement reads the checked set (delete 1+, merge 2+, label 1).
- **Insight:** A Treeview "checkbox" is a glyph in a cell plus programmatic selection — `identify_row`/`identify_column` locate the click, the glyph is just a cell value toggled with `tree.set`, and mirroring into native selection gives the row highlight for free. `selectmode="none"` makes the click handler the single source of truth, so the native selection can't fight the checkbox.

### SKU-04-03 — Refinement is a re-derive pipeline
- **Evidence:** commit `41a36a7` (`app/controllers/app_controller.py` — `_start_refinement`, `_refine_worker`)
- **Context:** `cycle_2_review.md` §5 flagged that merge/delete must recalculate the quality metrics. v0.3.0 also pre-generates the 5 static PNGs + 5 offline HTML files from the model, so a mutation invalidates them too.
- **Design Decision:** After a merge/delete, run a background pipeline: mutate the model → rebuild the result via `_build_result` → recompute `quality_metrics` → regenerate the 5 PNGs + 5 HTMLs → update `state.current_result`. The view shows the loading panel; the worker never touches the UI thread.
- **Observation:** The topics table, metrics gauges, and viz tabs all re-render from the updated result after each refinement; the UI stays responsive.
- **Insight:** A model mutation invalidates every artifact derived from it (metrics, visualisations). Refinement is "train-and-publish minus the training" — reuse the existing metric and visualisation services in a background worker rather than writing any new derivation logic.

## 2026-09-06 — Cycle 4 (v0.4.0), WP4: document exploration

### SKU-04-04 — Keep the original texts for search and display
- **Evidence:** commit `2058792` (`app/controllers/analysis_controller.py`; `app/models/algorithms/bertopic.py`)
- **Context:** Document exploration needs to search and display the documents, but the result's `metadata['texts']` holds only the **preprocessed** texts (lowercased, URLs/numbers/emails stripped) that were used for training.
- **Design Decision:** Store the original loaded texts as `metadata['original_texts']` at training time, and carry them through refinement — `merge_topics`/`delete_topics` copy them into the rebuilt result.
- **Observation:** Search matches the full original text (case-insensitive) and the Detail window shows the reader's document, not the preprocessed version; the preprocessed `texts` remain for training/metrics.
- **Insight:** The data a model trains on and the data a human reads can be different copies — keep both in the result metadata. Any step that rebuilds the result (like refinement's `_build_result`) must carry the user-facing copy forward explicitly, or it silently disappears after the first merge/delete.

### SKU-04-05 — Search the full text, not the rendered cell; Treeview over Tableview
- **Evidence:** commit `2058792` (`app/views/panels/summary_panel.py` — search row, `_build_doc_table`, `_doc_snippet`)
- **Context:** The Document Assignments table shows a 50-char snippet per document. To "find a document" the search must match the full text. ttkbootstrap's `Tableview` ships a built-in search bar, but it filters by the **displayed** cell values and is Enter-triggered rather than a button.
- **Design Decision:** Kept `ttk.Treeview`; added a search `Entry` + "Search" button (not per-keystroke) that filters `result.doc_topics` by full-text substring, and shows a window around the query match in the Document cell (with ellipses), plus a "Clear" button.
- **Observation:** Searching matches text beyond the visible 50-char snippet; the cell shows the match context; Enter on the entry also triggers the search.
- **Insight:** A widget's built-in search can be a trap — it operates on what is rendered, not what the user means to search. When a feature needs full-data matching with a custom snippet, filter the data yourself rather than adopting the widget's partial search, even though it saves a few lines.

### SKU-04-06 — Dual document filtering: by topic AND by text
- **Evidence:** commit `2058792` (`app/views/panels/summary_panel.py` — topic filter in `_build_doc_table`, `_rebuild_doc_table`)
- **Context:** Two complementary ways to find documents emerged: the raw idea (select topics in the topics table → see their documents) and search by content. They needed to compose.
- **Design Decision:** The Document Assignments table filters by both, AND-combined: docs whose Topic 1 (argmax) is one of the selected topics, further narrowed by the search query. Checking/unchecking a topic, searching, or clearing all rebuild the table through one `_rebuild_doc_table()`; a status label shows the active filters.
- **Observation:** Checking topic 0 shows only its documents; adding a query narrows within them; unchecking or Clear reverts.
- **Insight:** Two filter axes (by-topic, by-content) compose naturally with AND, and both are cheap view-layer filters over `doc_topics` — no model or query machinery needed. The argmax ("Topic 1") is the join key that ties the two tables together, which is exactly what makes the filter feel cohesive.
