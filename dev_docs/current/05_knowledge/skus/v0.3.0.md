## 2026-09-04 — Cycle 3 (v0.3.0), WP1: in-app visualisation tabs

### SKU-03-01 — In-app static visualisations via Plotly `to_dict()` + matplotlib
- **Evidence:** commits `c11178e`, `03a4a02`
- **Context:** The user wanted the BERTopic visualisations *inside* the app as tabs, not only opened in the browser. BERTopic's `visualize_*` methods return Plotly figures only. Rendering them statically in Tk requires a browser engine — kaleido needs a plotly upgrade plus an installed Chrome, and embedding a browser widget is heavy — all conflicting with the app's lightweight design.
- **Design Decision:** Read the rendered data out of the Plotly figure via `fig.to_dict()` (topic coordinates, marker sizes, labels, similarity matrix, dendrogram segments) and re-plot it with matplotlib (already a pinned dependency), dispatching on each trace's `type` (scatter / heatmap / bar / lines). The intertopic distance map — previously assumed the hard one — became easy because its exact 2D coordinates are already in the dict.
- **Observation:** All 5 visualisations render as clean static charts inside the app with no new dependency (no kaleido / Chrome / plotly upgrade). The converter had to translate Plotly's CSS colors (`rgb(61,153,112)`) to hex because matplotlib rejects that format.
- **Insight:** A research GUI gets the most value from an in-app static preview of every visualisation plus an "Open interactive" button for the real Plotly figure — immediate feedback without shipping a browser engine. The bridge is data: a Plotly figure's rendered data is reusable, not locked inside the HTML.

### SKU-03-02 — Pre-generate visualisations in the pipeline (user waits once, then everything is instant)
- **Evidence:** commit `03a4a02`
- **Context:** The first design generated each static chart lazily when its tab was opened, and generated the interactive HTML on click. The user found the tabs slow and hit reliability issues (blank browser tabs).
- **Design Decision:** Generate all 5 static PNGs + 5 offline HTML files in the training pipeline, immediately after the quality metrics. The user already waits during training — about 2 extra seconds on the sample corpus — so the added work is barely noticed.
- **Observation:** Tabs now open instantly, and "Open interactive" opens a stable, pre-existing file (nothing is generated on click), so the blank-tab race is gone.
- **Insight:** When users already wait for a long-running operation (training), front-load the expensive, once-only work into that wait rather than deferring it to repeated interactions. A few seconds during training is far less annoying than a wait — or a failure — every time they click something.

### SKU-03-03 — Serve interactive HTML over http://localhost instead of file:// (fixes blank browser tabs)
- **Evidence:** commit `03a4a02`
- **Context:** The "Open interactive" browser window intermittently opened blank even though the HTML file was complete (pre-generated, atomically written). The cause was not the file — browsers are simply unreliable at opening `file://` URLs.
- **Design Decision:** Serve the visualisation output directory over a tiny local HTTP server (bound to 127.0.0.1, ephemeral port, daemon thread) and open `http://localhost:<port>/<file>` in the default browser.
- **Observation:** Blank tabs disappeared; browsers navigate to `http://localhost` reliably, including on repeated clicks.
- **Insight:** A desktop app that shows local HTML in the browser should serve it over localhost rather than `file://` — `file://` causes intermittent blank tabs and stale caching across browsers.
