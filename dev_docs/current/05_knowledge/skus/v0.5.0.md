## 2026-09-07 — Cycle 5 (v0.5.0), WP2/WP3: model persistence

### SKU-05-01 — Persist the model with everything derived from it in a single project bundle
- **Evidence:** commits `b1e72eb` + `010cc26` (`app/models/services/project_service.py`; `app/models/algorithms/base_algorithm.py`; `app/models/algorithms/bertopic.py`)
- **Context:** Saving a project restored state and result data, but not the trained model or the visualisations — reloading meant retraining. The persistence design deferred from Cycle 4 specified a single-file zip bundle, but the format details (how to carry the model, how to stay multi-model-ready) were open.
- **Design Decision:** Reworked `ProjectService` to a zip-bundle `.stella` archive holding `project.json` (state + full result data) + `model/{model_id}/` (the trained model via per-algorithm `save_model`/`load_model` on `BaseAlgorithm`) + `viz/{model_id}/` (the pre-generated visualisations). `project.json` uses a `models` dict keyed by `model_id` (Option A), each entry carrying `selected_algorithm`, `algorithm_params`, and `result` — multi-model-ready without a `current_model_id`.
- **Observation:** A saved project reloads the same topics, metrics, and visualisations with the trained model restored — no retrain. The BERTopic feasibility check showed `model.save()` writes a **single pickle file, not a directory**, so the model is written as `model.pt` inside the per-model directory.
- **Insight:** A model is only as useful as the work derived from it — persisting the model together with its results and visualisations in one bundle makes "save and reload the full work" a single coherent artefact. Keying the bundle by `model_id` (rather than a single-model layout) costs little now and avoids a breaking format change when multi-model lands; and the per-algorithm save/load interface keeps persistence algorithm-agnostic, so LDA/NMF implement the same contract.
