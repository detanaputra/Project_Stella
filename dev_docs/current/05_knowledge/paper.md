## Key Ideas / Key Sentences

- SHAPR = **Solo, Human-centred, AI-assisted PRactice** — an operationalisation layer over Action Design Research (ADR).
- *"SHAPR enables structured traceability in AI-assisted research software development."*
- The cycle is **Explore → Build → Use → Evaluate → Learn**; the workflow rule is **Think → Code → Learn → Update (2 mins) → Repeat**.
- *"You cannot SHAPR everything"* — triage to decisions and learnings that influence behaviour and future choices.
- The human is the **epistemic authority**; the AI is a junior developer whose output is evaluated, not trusted.
- Evidence is the **translation of an interaction into artefact changes, documented in the repository** — not the chat transcript itself.

## Problem Formulation

**Research question:** *How can a topic modelling software be designed to provide a more accessible interface that enables non-technical users to perform topic modelling analysis?*

In this process, the RQ1 was explored further to define a Minimum Viable Product (MVP) which function as a scope that turns the broad goal of accessibility into a concrete, buildable trajectory rather than an open-ended design space. The MVP was defined as a tool for: 
1.	training topic model using available hyperparameter, 
2.	presenting the topics, terms, and the model configuration in plain forms, 
3.	measuring topic quality metric so users can assess the quality of the automated extraction
4.	merging, deleting, and labelling topics and interrogating them against the underlying documents; and 
5.	saving and reloading the full analysis, model and visualisations included, without retraining.

In the **Explore** phase of each SHAPR cycle, the scope for the next iteration was drawn from two sources. The first is the MVP feature list above: each cycle takes on one or more of these big features, keeping the trajectory anchored to the MVP. The second is the **gaps discovered from the previous cycle** — issues and risks surfaced by its evaluation, plus any designs carried forward as deferred, together supplying fixes and hardening. The human then triages the two: which MVP feature(s) to build now, which discovered gaps to fold in or defer, and what to postpone. Explore, in this process, is therefore a *scoping act rather than a discovery act* — the MVP defines the trajectory, and the previous cycle's gaps keep the current state honest.

Per cycle, the feature worked and the gap folded in from the previous cycle were:

| Cycle | Feature worked (MVP) | Gap from the previous cycle |
|---|---|---|
| 1 (v0.1.0) | Full MVP core — wizard, hyperparameters, result tables, save/load, browser visualisations, retrain (Agency) | — (no prior cycle) |
| 2 (v0.2.0) | Topic quality metrics — coherence and diversity (Evaluation) | — |
| 3 (v0.3.0) | In-app visualisation tabs + layout restructure (Interpretation) | — |
| 4 (v0.4.0) | Topic refinement + document exploration (Iteration) | C3 gap — random dialog placement (centred); C2 gap — metrics unexplained (plain-language explanations) |
| 5 (v0.5.0) | Model persistence — save/reload without retraining (Continuity) | C4 gap — no automated tests → test suite; plus the deferred persistence design from C4 |


## Observations

- **Case study:** Stella, a topic-modelling GUI for non-technical social scientists, built solo with AI assistance over five cycles (v0.1.0 build + audit/release; v0.2.0 metrics; v0.3.0 visualisation tabs + layout restructure; v0.4.0 topic refinement + document exploration; v0.5.0 test suite + model persistence).
- **Cycle 1 (v0.1.0):** full MVC application (wizard, result tables, `.stella` save/load, pywebview visualizations, retrain); 25 SKUs after triage.
- **Cycle 1 review (v0.1.1):** a read-only audit found 22 issues; fixes by severity, one commit per class; released.
- **Cycle 2 (v0.2.0):** README + Apache 2.0 license, MouseWheel scrolling, topic quality metrics (NPMI, C_V, UMass, Topic Diversity) via Gensim; 4 SKUs.
- **Footprint check:** OCTIS (0.13 MB package) would have pulled torch (~1–2 GB installed); Gensim's `CoherenceModel` covered all three coherence measures at a fraction of the footprint.

## Patterns / Insights

- **Audit-as-cycle-review** — the v0.1.1 audit was, in SHAPR terms, a review of Cycle 1 rather than a new cycle; this reframing produced `cycle_1_review.md`.
- **SKU triage** — 55 SKUs including trivial ones (sash thickness, `.gitignore`) were consolidated to 25 design-changing SKUs; a numbering scheme is a contract, and changing it has a documentation ripple.
- **Footprint checks before adopting research libraries** — a quick wheel-size/dependency check can save gigabytes of bundle size and dependency conflicts.
- **Human-captures / AI-consolidates** — the human directs scope and judgement; the AI consolidates, restructures, and aligns notes at deliberate checkpoints.
- **Snapshot → reset → next cycle improves clarity** — frozen snapshots at cycle boundaries give each cycle a clean baseline.
- **Explore is scoping, not discovery** — the defined MVP/roadmap supplies the feature arc and prior-cycle gaps (and deferred designs) supply fixes and hardening; the human's triage, not fresh ideation, selects each cycle's scope.

## Design Principles

Distilled from the "Key Learning Confirmed" section of each cycle review (`dev_docs/cycle_record_notes/cycle_N_review.md`). Each principle follows the form: *To allow [audience] to [goal], develop [functionality], because [rationale].*

### Cycle 1 — Principle of Agency
To allow topic model practitioners to control and reproduce their topic models when doing topic modelling analysis, develop functionality that exposes the algorithm's hyperparameters to the user through the interface, because the ability to set and adjust the model parameters is essential for researchers to tailor the automated topic extraction to their data and document the configuration for reproducibility.

### Cycle 2 — Principle of Evaluation
To allow topic model practitioners to assess topic quality when doing topic modelling analysis, develop functionality that enables users to measure topic quality metrics such as topic coherence and topic diversity, because of the requirement to evaluate the accuracy and usefulness of the automated topic extraction.

### Cycle 3 — Principle of Interpretation
To allow topic model practitioners to explore and interpret their models when doing topic modelling analysis, develop functionality that enables users to view the visualisations directly in the application, because visual inspection of the model output is essential for evaluating the usefulness and interpretability of the automated topic extraction.

### Cycle 4 — Principle of Iteration
To let topic model practitioners treat topic modelling as an iterative, interpretable process rather than a one-shot output, develop functionality that lets them act on the model (merge, delete, and label topics) and interrogate it against the data (search and inspect the documents behind each topic), because a model is only useful to a researcher when they can refine it and verify its topics against the actual documents.

### Cycle 5 — Principle of Continuity
To allow topic model practitioners to preserve and resume their analysis work when doing topic modelling analysis, develop functionality that persists the trained model together with its results and visualisations in a single project bundle, because the ability to save and reload the full work without retraining is essential for researchers to continue their analysis across sessions and reproduce their findings.

- **Methodology paragraph:** This project applies SHAPR — a solo, human-centred, AI-assisted practice framework — to the development of Stella, a topic-modelling desktop application for non-technical social scientists. SHAPR operationalises Action Design Research by making explicit the roles, artefacts, reflective practices, and lightweight governance mechanisms needed for accountability in AI-assisted development. The framework's evidence and traceability mechanism links human decisions, AI-assisted development, and artefact evolution, enabling transparency, reproducibility, and systematic refinement.

- **Collaboration pattern paragraph:** Throughout the project, the human researcher acted as the epistemic authority, directing scope and judging the AI's output against constraints, while the AI acted as a junior developer — drafting code, consolidating notes, and restructuring documentation at deliberate checkpoints. This division of labour kept the human in control of what is true while leveraging the AI's capacity for boilerplate and consolidation.

- **Architecture paragraph (MVC):** Stella is designed according to the Model-View-Controller (MVC) architectural pattern, which partitions the application into three layers with clearly separated responsibilities. The **model layer** contains all data and computation and is deliberately free of interface code. At its centre lies an application state — the single source of truth that every part of the interface reads from — beside a standardised result structure that holds the discovered topics, their terms, the per-document assignments, and the model configuration. Algorithms are interchangeable: each implementation conforms to a common contract, of which BERTopic is currently the sole realisation, so that additional algorithms can be introduced without altering the rest of the application. Around these sit a set of services that handle the supporting operations: loading and validating the input documents, executing the modelling pipeline, computing topic-quality metrics, generating static and interactive visualisations, exporting results in common formats, and saving and restoring whole projects. The **controller layer** orchestrates user actions: one controller (AppController) manages configuration and secondary operations such as file selection, parameter adjustment, results export, topic refinement, and project persistence, while a second controller (AnalysisController) runs the computationally demanding training pipeline in the background. The **view layer** is concerned solely with presentation: a guided wizard leads the user through project setup, and a collection of panels renders the topics, quality metrics, visualisations, document assignments, and processing status, all obtained from the application state. Communication flows in one direction — views invoke controllers, controllers manipulate the model and update the state, and views re-render from the state — which keeps interface concerns, data logic, and algorithm implementations separable and independently evolvable.

- **State synchronisation paragraph (Observer):** Coordination between the layers is achieved with an observer pattern built around the application state. When a view is created it registers itself with the state; whenever the state changes — after a training run, a topic refinement, or a project reload — the state notifies all registered views, and each re-draws the parts of the interface that depend on the changed data. Because the state is the shared hub and views only read from it, no view keeps its own copy of the data and no view depends on another's internals. The same mechanism reconciles threading with responsiveness: the expensive stages of the modelling pipeline run on background threads, and those threads interact with the interface only through the state, which schedules the resulting update to run on the main thread. The interface therefore remains responsive and reflects progress as it happens, and, because the model layer never touches the interface, the state and logic layer can be tested without a graphical environment — a property that became the foundation of the automated test suite introduced at a later stage of the project.

- **Layout paragraph (two-column workspace):** The main window follows a two-column layout in which the two analytical tasks — configuring the model and inspecting its output — occupy separate, dedicated zones. The left column is a persistent hyperparameter panel where the user sets the modelling options: the algorithm's hyperparameters and the parameters of the underlying dimensionality-reduction and clustering steps. Because this panel remains visible and fixed throughout a session, the configuration can be reviewed and adjusted at any moment without navigating away. The right column is a tabbed results workspace that the application progressively extends as an analysis matures: an analysis tab presents the discovered topics and the per-document assignments, a metrics tab reports the topic-quality measures, and a set of visualisation tabs renders the structure of the model. Earlier in development this zone was accompanied by a separate toolbox of action buttons and a right-side parameter strip; a layout restructure removed the redundant toolbox, moved the parameters into their persistent left column, and relocated the remaining global actions (export and settings) into the file menu. The result is a stable partitioning by role — configure on the left, observe, evaluate, and refine on the right — which mirrors the analyst's alternating rhythm of tuning the model and inspecting what it produces.

- **Evaluation paragraph (Cycle 1):** The evaluation of Cycle 1 drew on the release audit that followed the v0.1.0 build. **H1** (simple and natural dialog) was assessed against the guided four-step wizard, which was judged to present only the information needed at each stage; the audit's low-priority fixes additionally removed dead views and stub menus, so the dialog held no unreachable or irrelevant controls. **H2** (speak the user's language) was assessed against the wizard by design: guidance is phrased in the plain language of its non-programmer audience rather than in machine or library terms. **H4** (consistency) was checked across the two surfaces that expose model parameters — the wizard and the settings panel — and passed because the same prefixed parameter keys are reused identically in both with no collisions. **H5** (feedback) was assessed against the training flow, which runs in the background and reports stage-based progress through a loading panel and status text. **H7** (shortcuts) was satisfied by the standard editing accelerators provided through the Edit menu. **H8** (good error messages) was assessed against file import: validation responds in plain language (sample-size and document-length advisories) and encoding failures are reported rather than raised as raw exceptions. **H9** (prevent errors) was assessed against the parameter boundary and the training path: parameter ranges are clamped for small corpora, duplicate training runs are guarded, and a failing callback cannot freeze the whole interface. **H3**, **H6**, and **H10** were not tested — H3 (minimise the user's memory load) because no cross-panel design for recall was documented, H6 (clearly marked exits) because no reversible state mechanism had yet surfaced to evaluate, and H10 (help and documentation) because it is intentionally out of scope for the desktop tool, whose guidance lives in the external README.

- **Evaluation paragraph (Cycle 2):** The evaluation of Cycle 2 concerned the new metrics interface. **H1** was assessed against the Metrics tab, which passed as a single focused screen of four topic-quality gauges that did not clutter the existing tabs. **H2** was assessed against the same gauges and **failed**: the four measures of coherence and diversity were displayed as bare numbers with no explanation, a gap the cycle's own review acknowledged as unfriendly to beginners. The remaining heuristics were not tested for lack of relevant change: the cycle otherwise produced no new dialog (so H3, H6), no new error or prevention logic (H8, H9), no second surface for a consistency check (H4), no progress-bearing interaction to extend the feedback findings of the previous cycle (H5), and no new input conveniences beyond scroll-wheel support in the parameter panels, which is not an accelerator and thus not H7.

- **Evaluation paragraph (Cycle 3):** The evaluation of Cycle 3 concerned the layout restructure and the arrival of in-app visualisations. **H1** was assessed against the main window: a redundant toolbox was removed, the hyperparameter panel was fixed into a persistent left column, and the global actions (export and settings) were relocated into the file menu — a partitioning the cycle's review described as less redundant and more intuitive. **H5** was assessed against the visualisation tabs: all charts are pre-generated during training, so the tabs and their interactive counterparts open instantly, eliminating the delayed responses that on-demand generation had caused. The remaining heuristics were not tested because the cycle changed no other interaction: the new tabs introduced no dialogs (H2, H3, H6), no new error or prevention logic (H8, H9), no accelerators (H7), and none of the changed surfaces had a counterpart that a consistency check (H4) could compare.

- **Evaluation paragraph (Cycle 4):** The evaluation of Cycle 4 covered the richest set of changes — topic refinement, document exploration, and several interface refinements. **H1** was assessed against the dialogs and the document detail window: every top-level dialog is now centred on the main window, and the detail view shows only the document index, its topic probabilities, and the full text. **H2** was assessed against the metrics screen and the refinement toolbar: plain-language explanations were added to the previously opaque gauges, the option set was limited to a single embedding model and language so users are not confronted with technical alternatives, and toolbar buttons carry both an icon and a text label after icon-only buttons were found unclear. **H3** was assessed against document search: searching is triggered by an explicit button with a clear reset, and a status label keeps the active filters visible, so the user need not hold the query state in memory while inspecting results. **H4** was assessed against the topics table, where the checkbox glyph, the row highlight, and the enabled state of the refinement buttons are all driven by the same selection, so the interface never contradicts itself. **H5** was assessed against the refinement pipeline: destructive actions are preceded by confirmation dialogs, and the background re-derivation of metrics and visualisations is surfaced by a loading panel. **H6** was assessed against those same confirmations: each offers a clear cancel so an unintended merge or deletion can be aborted before its effect, and the document search offers an explicit clear. **H9** was assessed against the refinement controls: buttons stay disabled until the selection is valid (one topic for deletion, two for a merge), and the destructive operations run only after confirmation. **H7** was not tested because no new accelerators were introduced, **H8** because the cycle added no new error-reporting path, and **H10** remained out of scope.

- **Evaluation paragraph (Cycle 5):** The evaluation of Cycle 5 was necessarily indirect, because the cycle's work — an automated test suite and model persistence — added no new interaction surfaces. **H9** (prevent errors) was assessed in two senses: the committed test suite acts as a quality gate that caught a genuine runtime crash before release, and the persistence feature protects users from losing trained work by restoring the whole project without retraining. The remaining heuristics were not tested against new behaviour because the interface itself was unchanged: the save/load dialogs and the results workspace evaluated in earlier cycles were left as they were, and no new panels, dialogs, error paths, or shortcuts were introduced (H1–H4, H6–H8, H10).

- **Feature paragraph (Hyperparameter tuning):** Hyperparameter tuning is the primary interface through which the user controls the modelling algorithm, and it embodies the first design principle, that of agency. Rather than treating the analyser as a black box, the application exposes the training options directly: the user sets the topic-model hyperparameters (the number of terms shown per topic, the range of n-grams, the minimum topic size, and related options) together with the parameters of the two steps that precede the model itself — the dimensionality-reduction step and the clustering step. The parameter form is not hard-coded to one algorithm; it is generated from a schema that each algorithm declares, so the same interface adapts when a different algorithm is introduced. The settings appear in two places that stay in sync — the guided setup wizard and a persistent panel on the left of the main window — so the configuration can be adjusted both before analysis and between successive runs, and a model can be reproduced from the recorded configuration. The current release deliberately limits the option set to a single embedding model and language, keeping the choices manageable for its non-programmer audience.

- **Feature paragraph (Evaluation metrics):** The evaluation-metric feature addresses a researcher's need to judge whether an automated extraction is trustworthy, and it embodies the second design principle, that of evaluation. After training, the application reports four measures of topic quality on a dedicated screen: three coherence scores that capture how semantically related the words within a topic are, computed over each topic's most representative terms on the training corpus, and a diversity score that measures how distinct the topics are from one another. The metrics are computed in the background as part of the training pipeline and are recalculated whenever the user refines the topics, so the quality reading always corresponds to the current model. Each gauge is accompanied by a plain-language explanation of what the measure means, so that a researcher without a computational background can interpret it rather than treat it as a bare number.

- **Feature paragraph (Static and interactive visualisation):** Building on the third design principle, that of interpretation, the application renders the structure of the trained model in five complementary views: the topic-word distributions, the inter-topic distance map, the term frequencies within each topic, the topic hierarchy, and the topic-word rankings. Each view exists in two forms: a static chart embedded in the application, and an interactive version that opens in a web browser and can be explored — zooming, hovering over individual points, and selecting. Both forms are produced automatically during training rather than on demand, so the embedded charts appear instantly when the user opens a tab and the interactive files are stable artefacts that can be shared. The static charts give an immediate in-app reading of the model, while the interactive figures preserve the exploratory power needed to interrogate it.

- **Feature paragraph (Topic refinement and document exploration):** The refinement and exploration features together make the analysis an iterative, interpretable process rather than a one-shot output, embodying the fourth design principle, that of iteration. After a model is trained, the user can act directly on the discovered topics: select topics in the results table and merge two or more into one, delete topics whose content is unwanted, or attach a descriptive label. Destructive operations are confirmed before they run and are only offered once the selection is valid, so an unintended merge or deletion cannot slip through. Every mutation is followed by an automatic re-derivation in the background, so the tables, metrics, and visualisations are recomputed from the modified model and the interface never shows stale results. Complementing this, the user can interrogate the model against its source data: search the full text of the documents, filter the assignment table down to the topics currently selected, and open any document to see its index, its probability distribution across all topics, and its complete text — the checks a researcher needs to verify that a topic means what it appears to mean.

- **Feature paragraph (Model persistence):** Model persistence closes the analytical loop by letting the researcher preserve and resume their work, embodying the fifth design principle, that of continuity. Saving a project bundles everything the analysis depends on into a single project file: the configuration and full result data, the trained model itself, and the visualisations. Because the model is saved rather than discarded, reloading a project restores the same topics, metrics, and charts without retraining — essential when modelling is expensive and analysis is spread across many sessions. Models are stored through an interface shared by all algorithms, so persistence does not depend on which algorithm produced the model, and each saved model carries an identifier, so a single project can later hold more than one model. The result is one artefact that carries the researcher's full body of work forward.

- **Evaluation summary paragraph (1) — what held across the cycles:** Three heuristics pass wherever the cycles gave them an interaction to examine. **H1** (simple and natural dialog) holds in every cycle that changed the interface: the guided wizard in Cycle 1, the single focused metrics screen in Cycle 2, the reduced layout in Cycle 3, and the centred, minimal dialogs in Cycle 4. **H5** (feedback) holds wherever a waiting interaction exists: background training with stage-based progress in Cycle 1, visualisations pre-generated so the tabs open instantly in Cycle 3, and the loading panel and confirmation dialogs that accompany refinement in Cycle 4. **H9** (prevent errors) holds on every risk-bearing path: parameter clamping and the guard against duplicate training in Cycle 1, selections kept invalid until they are usable and destructive actions gated by confirmation in Cycle 4, and — indirectly — the test suite that acts as a pre-release quality gate in Cycle 5. These three, together with **H2** once its failure below was remedied, form the application's dependable core.

- **Evaluation summary paragraph (2) — the one failure, its cause, and its fix:** The only documented failure is **H2** (speak the user's language) in Cycle 2. The newly introduced evaluation screen presented four topic-quality gauges — coherence and diversity — as bare numbers. For the non-programmer audience those figures carried no meaning, and the cycle's own review acknowledged that the screen was "not user-friendly for beginners". The root cause is a tension specific to this feature: the metrics were added precisely to measure quality, yet delivering them as raw statistical values reproduces the jargon the design philosophy was meant to remove. The remedy arrived two cycles later, in Cycle 4: a plain-language explanation was attached to each gauge, the option set was reduced to a single embedding model and language so no technical alternatives remained to confuse the user, and the refinement toolbar switched from icon-only buttons to icon-plus-text. H2 has held since. (One within-cycle defect is worth noting separately: an audit finding in Cycle 1 — the parameter form rebuilt itself on every keystroke and destroyed the user's edit mid-typing — was found and fixed inside the cycle's own review, after which the form rebuilt only when the structure, not the value, changed.)

- **Evaluation summary paragraph (3) — what was not assessed and why:** Only a subset of the heuristics could be exercised, and the coverage is concentrated where the cycles produced observable interface behaviour. **H10** (help and documentation) is deliberately out of scope in every cycle: the desktop tool ships no in-app help, and guidance lives in the external README. **H7** (shortcuts) is assessed once — the standard edit accelerators of Cycle 1 — and never again, because no later cycle added new accelerators. **H3** (minimise the user's memory load) and **H6** (clearly marked exits) are each assessed only in Cycle 4, where document search introduced a recall-relevant state (resettable search with a visible filter status) and refinement introduced reversible-action surfaces (confirmation dialogs with a cancel); in earlier cycles no cross-panel state nor reversible mechanisms existed to examine. **H8** (good error messages) is assessed in Cycle 1, where file validation returns plain-language advisories rather than raw exceptions, and is then absent because no later cycle added a new error-reporting path. The same pattern explains the sparse coverage of the narrow-feature cycles (2 and 3) and the back-end cycle (5): a reconstruction can only rate heuristics where the development documentation records behaviour worth judging, so the assessments concentrate on the interaction-bearing cycles 1 and 4.

## Heuristic Evaluation (Nielsen, 1994)

A retrospective evaluation of Stella's user interface per build cycle. Each cycle is assessed against Nielsen's ten usability heuristics; only heuristics with documented evidence are evaluated, the rest are marked *Not Available*. **10. Help and documentation** is consistently out of scope for the desktop MVP (guidance lives in the external README), and **7. Shortcuts** only applies where accelerators were added. Verdicts are reconstructions from documented behaviour, not fresh observations — they should be confirmed with a live walkthrough before being cited. The heuristic evaluation is presented as evaluation evidence that corroborates each cycle's design principle (the Learn output), not as the source of it.

### Cycle 1 (v0.1.0 + v0.1.1 audit)
- **1. Simple and natural dialog — Satisfied.** A guided 4-step wizard carries setup; the audit's L-fixes removed dead views and stub menus, so the dialog holds no unreachable or irrelevant controls.
- **2. Speak the user's language — Satisfied (by design).** The app targets non-technical social scientists under the stated philosophy "clarity over aesthetics — plain language, no jargon", and the wizard guides project setup in those terms.
- **4. Consistency — Satisfied.** Hyperparameter sections use prefixed state keys reused identically across the two surfaces that expose them (wizard + settings panel) with no key collisions, and the wizard's default parameters sync with the same settings.
- **5. Feedback — Satisfied.** Training runs in a background thread with milestone-based progress reporting and a live loading panel (`analysis_progress` / `analysis_status` in `AppState`).
- **7. Shortcuts — Satisfied.** Standard Edit-menu accelerators (cut/copy/paste/undo/redo) are present.
- **8. Good error message — Satisfied.** `DataLoader.validate_file` returns research guidance (small/moderate sample-size warnings, average document-length checks) rather than raw exceptions, and the CSV loader reports encoding problems cleanly with a UTF-8 → Latin-1 fallback.
- **9. Prevent errors — Satisfied.** Parameter validation clamps UMAP neighbours and n-gram range for small corpora; a re-entrancy guard prevents duplicate training; exception-isolated event processing stops one bad callback from freezing the UI. The audit also found and fixed H1 — the parameter form rebuilt on every keystroke, destroying the user's edit mid-typing.
- **Not Available:** 3, 6, 10.
